一、串行 · 并行 · 限流怎么选

必练

Q1 · 三种执行策略分别适合什么场景？

📌 场景

相册页用户选了 100 张 图片要上传，后端限流「单用户最多同时 3 个连接」。你会怎么设计？和「一张一张传」「100 个一起传」有何区别？

查看答案
策略写法思路耗时典型场景
串行 for (const t of tasks) await t() 累加（100×单次） 有严格顺序依赖、写后读
全并行 Promise.all(tasks.map(t => t())) ≈最慢那个 少量独立请求、无服务端限流
限流并发 runPool(tasks, 3) 介于两者之间 批量上传、爬虫、分页拉取

上面场景答案：用限流并发 3——既比串行快，又不会触发 429 / 浏览器连接数打满。

面试口诀：要顺序 → 串行；要最快且量小 → all；量大要控节奏 → 线程池 / runPool。

必练

Q2 · 批量拉 10 个详情，允许部分失败怎么写？

📌 场景

列表页拿到 10 个 id，要并行拉详情渲染卡片。其中 1 个 id 已删除会 404—— 你希望其它 9 个仍展示，而不是整页报错白屏。用 all 还是 allSettled？

查看答案

选 Promise.allSettled（或每个请求单独 catch 后返回 null）。

const ids = [1, 2, 3 /* ... */];

const results = await Promise.allSettled(
  ids.map((id) => fetch(`/api/item/${id}`).then((r) => r.json()))
);

const items = results
  .filter((r) => r.status === 'fulfilled')
  .map((r) => r.value);

const failed = results.filter((r) => r.status === 'rejected');
// 可对 failed 打日志或展示占位
API一个失败时
Promise.all立刻 reject，适合「全部成功才算成功」
Promise.allSettled等全部结束，逐项看 status
Promise.any任一成功即成功（竞速/备用源）

静态方法细节见 Promise Q12。

二、Promise.all 的坑

必练

Q3 · all 里一个失败，其它请求还在跑——怎么办？

📌 场景

下单页要同时校验库存、优惠券、地址三个接口，用 Promise.all。 库存接口先返回「无货」——你希望立刻取消另外两个还在飞的请求，避免无效计算和用户多等。

查看答案

坑：Promise.all reject 后不会自动 abort 其它 fetch，它们仍会跑完（浪费带宽）。

解法：统一 AbortController，任一失败时 abort()：

async function validateCheckout() {
  const controller = new AbortController();
  const { signal } = controller;

  const tasks = [
    fetch('/api/stock', { signal }),
    fetch('/api/coupon', { signal }),
    fetch('/api/address', { signal }),
  ];

  try {
    return await Promise.all(tasks);
  } catch (e) {
    controller.abort(); // 取消其余进行中的请求
    throw e;
  }
}

面试答法：「all 只负责聚合结果，不负责取消；生产上要自己用 AbortController 或标志位。」

选练

Q4 · forEach 里写 async 为什么不会「等全部完成」？

📌 场景
const ids = [1, 2, 3];

ids.forEach(async (id) => {
  await saveItem(id);
});
console.log('全部保存完成'); // 实际会先打印这行

保存草稿时踩坑：以为 forEach + await 会串行等完，结果提前提示「保存成功」。

查看答案

原因：forEach 不会等待 async 回调；它同步触发 3 个 async 函数后立即继续，console.log 先执行。

正确写法：

// 并行等全部
await Promise.all(ids.map((id) => saveItem(id)));

// 串行
for (const id of ids) {
  await saveItem(id);
}

同类坑：map 不 await 也会 fire-and-forget；reduce 链可实现串行（选练）。

三、手写并发限流（面试最高频）

必练

Q5 · 手写 runPool：最多同时 N 个

📌 场景

100 张图片上传，tasks[i] = () => upload(file[i])， 要求最多 3 个同时进行，全部完成后按原顺序返回结果数组。

查看答案

思路：开 limit 个 worker，共享递增下标 index，谁空闲谁取下一个 task。

async function runPool(tasks, limit) {
  const results = new Array(tasks.length);
  let index = 0;

  async function worker() {
    while (index < tasks.length) {
      const cur = index++;
      results[cur] = await tasks[cur]();
    }
  }

  const workers = Array.from(
    { length: Math.min(limit, tasks.length) },
    () => worker()
  );
  await Promise.all(workers);
  return results;
}

// 使用
await runPool(files.map((f) => () => upload(f)), 3);

口述要点：

  • 任务用函数数组 () => Promise，避免一启动就全执行
  • index++ 在 async 里是原子取用（单线程无竞态）
  • 结果按 cur 下标写，保证顺序

复杂度：约 O(总数) 时间，同时最多 limit 个 in-flight。

选练

Q6 · 滑动窗口 vs 线程池写法有何不同？

📌 场景

面试官追问：「除了 worker 池，能不能用队列 + 执行中计数实现？」——两种思路都要能讲。

查看答案

写法 A — worker 池（Q5）：固定 N 个 worker 循环取任务，最常用、好写。

写法 B — 滑动窗口 / 链式：维护 executing 集合，满了就 Promise.race 等任意一个完成再补：

async function poolRace(tasks, limit) {
  const ret = [];
  const executing = new Set();

  for (const [i, task] of tasks.entries()) {
    const p = Promise.resolve().then(() => task()).then((val) => {
      ret[i] = val;
      executing.delete(p);
    });
    executing.add(p);
    if (executing.size >= limit) {
      await Promise.race(executing);
    }
  }
  await Promise.all(executing);
  return ret;
}

面试能讲清 Q5 即可；B 作加分项。

四、重试 & 容错

必练

Q7 · 手写 retry：失败重试 3 次

📌 场景

支付结果查询接口偶发 502，产品要求：失败后最多重试 3 次， 每次间隔 500ms，仍失败再提示用户。

查看答案 
function sleep(ms) {
  return new Promise((r) => setTimeout(r, ms));
}

async function retry(fn, times, delay = 0) {
  let lastError;
  for (let i = 0; i < times; i++) {
    try {
      return await fn();
    } catch (e) {
      lastError = e;
      if (i < times - 1 && delay > 0) {
        await sleep(delay);
      }
    }
  }
  throw lastError;
}

// 使用
await retry(() => fetchPaymentStatus(orderId), 3, 500);

进阶（口述）：

  • 仅对 5xx / 网络错误重试，4xx 不重试
  • 指数退避：500ms → 1s → 2s
  • retry + runPool：每个任务独立 retry
选练

Q8 · 限流 + 单任务失败不拖垮整批

📌 场景

批量导入 50 条 Excel 行，每行调一次 API，并发限制 5。 某一行校验失败不应导致整批中断，最后要汇总成功数 / 失败列表。

查看答案 
async function runPoolSettled(tasks, limit) {
  const wrapped = tasks.map(
    (task, i) => () =>
      task()
        .then((value) => ({ index: i, status: 'fulfilled', value }))
        .catch((reason) => ({ index: i, status: 'rejected', reason }))
  );
  return runPool(wrapped, limit);
}

// 使用
const results = await runPoolSettled(
  rows.map((row) => () => importRow(row)),
  5
);
const ok = results.filter((r) => r.status === 'fulfilled');
const bad = results.filter((r) => r.status === 'rejected');

思路：每个 task 内部 catch 成 fulfilled 结果对象，外层 runPool 不会因单个 reject 而整体失败。

五、取消 & 超时

必练

Q9 · 切换 Tab 时取消进行中的搜索请求

📌 场景

用户快速切换「商品 / 店铺 / 用户」三个 Tab，每个 Tab 会发搜索请求。 旧 Tab 的慢请求后返回，把新 Tab 的结果覆盖掉——怎么防？

查看答案

方案 1 — AbortController（推荐）：

let controller = null;

async function search(tab, keyword) {
  controller?.abort();
  controller = new AbortController();

  const res = await fetch(`/api/search?tab=${tab}&q=${keyword}`, {
    signal: controller.signal,
  });
  return res.json();
}

方案 2 — 请求序号 / 标志位：每次搜索递增 reqId，响应回来时比对是否仍为最新。

React Strict Mode / 组件卸载：useEffect cleanup 里 abort()，避免 setState on unmounted component。

选练

Q10 · 接口超时 timeout(promise, ms)

📌 场景

第三方地图 API 有时 30s 无响应，产品要求 5s 内必须给出结果或超时提示。 手写 timeout(promise, ms)。

查看答案 
function sleep(ms) {
  return new Promise((r) => setTimeout(r, ms));
}

function timeout(promise, ms) {
  return Promise.race([
    promise,
    sleep(ms).then(() => Promise.reject(new Error('timeout'))),
  ]);
}

// 使用
try {
  const data = await timeout(fetchMap(lat, lng), 5000);
} catch (e) {
  if (e.message === 'timeout') showToast('请求超时');
}

注意：race 超时后原 promise 仍在跑，和 Q3 一样若需省资源应配合 AbortController。

function timeoutSignal(promise, ms, controller) {
  const timer = setTimeout(() => controller.abort(), ms);
  return promise.finally(() => clearTimeout(timer));
}
