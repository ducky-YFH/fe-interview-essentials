一、基础概念

必练

Q1 · Event Loop 是什么？用一句话解释

📌 场景

用户点击「提交」后，你写了 setTimeout(() => toast('成功'), 0) 想「尽快」弹提示， 却发现页面先卡顿了一下才弹出——为什么 0ms 也不是立刻执行？

查看答案

Event Loop（事件循环）：JS 单线程，同步代码执行完后， 引擎反复「取一个宏任务执行 → 清空微任务队列 →（浏览器可能渲染）→ 再取下一个宏任务」的循环机制。

上面场景：

  • setTimeout(fn, 0) 只是把回调放进宏任务队列，等当前同步代码和所有微任务跑完才轮到
  • 浏览器里 0ms 通常还有最小延迟（嵌套 timer 约 4ms）
  • 所以「0」≠ 立即，只是「尽快排进宏任务」

面试口述：

「JS 是单线程，异步靠事件循环调度。同步代码先跑完，再处理微任务， 再取宏任务，循环往复。」

必练

Q2 · 宏任务和微任务分别有哪些？

📌 场景

接口返回后同时做了三件事： Promise.then(renderData)、 setTimeout(trackLog, 0)、 requestAnimationFrame(updateChart)。 谁先执行？依据是什么？

查看答案
类型常见来源
微任务 Promise.then/catch/finally、 queueMicrotask、 MutationObserver、 async/await（await 之后相当于微任务）
宏任务 setTimeout / setInterval、 setImmediate（Node）、 I/O 回调、UI 渲染事件、postMessage 等

上面场景大致顺序（浏览器）：

  1. 当前同步代码结束
  2. 微任务：Promise.then(renderData)
  3. 可能渲染页面
  4. 宏任务：setTimeout(trackLog)
  5. requestAnimationFrame 在下一帧绘制前，通常在本轮微任务清完之后、与渲染管线相关（面试答「在宏任务之后、绘制前」即可）

铁律：每执行完一个宏任务，都会清空当前所有微任务，再考虑渲染/下一个宏任务。

二、经典输出题

Q3 · 入门级输出顺序

📌 场景

页面初始化时同时打日志、注册 Promise、设 setTimeout——面试最高频的一题，必须秒答。

console.log('A');

setTimeout(() => console.log('B'), 0);

Promise.resolve()
  .then(() => console.log('C'))
  .then(() => console.log('D'));

console.log('E');
查看答案

输出：A → E → C → D → B

  1. 同步：A、E
  2. 微任务队列：C，然后 D（第二个 then 在本轮微任务里继续注册并执行）
  3. 宏任务：B

口诀：同步 → 微任务清空 → 宏任务一个 → 再微任务 → …

必练

Q4 · 宏任务里再注册微任务

📌 场景

埋点 SDK 用 setTimeout 延迟上报，上报前又用 Promise 整理数据—— 嵌套异步时顺序容易晕，跑一遍就懂。 

console.log('start');

setTimeout(() => {
  console.log('timeout1');
  Promise.resolve().then(() => console.log('promise-in-timeout'));
}, 0);

Promise.resolve()
  .then(() => {
    console.log('promise1');
    setTimeout(() => console.log('timeout2'), 0);
  })
  .then(() => console.log('promise2'));

console.log('end');
查看答案

输出：

start → end → promise1 → promise2 → timeout1 → promise-in-timeout → timeout2
  1. 同步：start、end
  2. 微任务：promise1（注册 timeout2）→ promise2
  3. 宏任务 timeout1 → 其内部微任务 promise-in-timeout
  4. 宏任务 timeout2

关键：每个宏任务执行完后，都会先把新产生的微任务全部跑完，再取下一个宏任务。

必练

Q5 · async/await 输出顺序

📌 场景

用 async 函数拉取用户信息，await 之后更新 UI 又注册了一个 Promise—— 和 Promise 专题 Q11 同一类，这里单独再练一遍。 

async function loadUser() {
  console.log('1');
  await Promise.resolve();
  console.log('2');
  Promise.resolve().then(() => console.log('3'));
  console.log('4');
}

loadUser();
console.log('5');
查看答案

输出：1 → 5 → 2 → 4 → 3

  1. 同步：1，遇到 await 暂停，后续代码作为微任务
  2. 同步继续：5
  3. 微任务（await 续体）：2 → 注册 3 的微任务 → 4
  4. 同一轮微任务队列下一个：3

记忆：await = 把后面的代码包进 .then；await 后面的同步代码仍在同一个微任务里顺序执行。

三、浏览器 & 项目场景

选练

Q6 · 微任务连环嵌套输出什么？

📌 场景

链式 .then 里又 return Promise.resolve()， 中间层异步调度容易漏题——检验是否真懂「微任务清空」。 

Promise.resolve()
  .then(() => {
    console.log('then1');
    Promise.resolve().then(() => console.log('then2'));
  })
  .then(() => console.log('then3'));

console.log('sync');
查看答案

输出：sync → then1 → then2 → then3

  • 同步 sync
  • 第一个 then 执行 then1，内部注册的 then2 进入微任务队列
  • 第一个 then 返回 undefined，第二个 then（then3）也进微任务队列
  • 清空微任务：then2 → then3

坑：以为 then3 一定在 then2 前——错，同一轮里按注册顺序执行。

选练

Q7 · requestAnimationFrame 和微任务谁先？

📌 场景

列表滚动时用 rAF 做虚拟列表重绘，同时在 Promise 里更新了数据—— 想保证「数据先更新，再绘制」，该怎么排？ 

console.log('script');

Promise.resolve().then(() => console.log('microtask'));

requestAnimationFrame(() => console.log('rAF'));

console.log('script-end');
查看答案

典型输出：script → script-end → microtask → rAF

浏览器渲染管线（简化）：

  1. 执行 JS（宏任务 / 同步脚本）
  2. 清空微任务
  3. （必要时）样式计算、布局、绘制
  4. requestAnimationFrame 回调在下一帧绘制前

项目建议：数据变更放微任务或同步；DOM 测量/动画放 rAF，避免 layout thrashing。

必练

Q8 · setState 后立刻读 DOM 为什么还是旧的？

📌 场景
function handleClick() {
  setCount(count + 1);
  console.log(ref.current.textContent); // 还是旧值？
  ref.current.textContent = '已更新';    // 和 React 状态不同步
}

Vue / React 里改状态后马上量高度、读 DOM 经常踩坑——和 Event Loop 什么关系？

查看答案

原因：

  • setState / setCount 不会同步改 DOM，而是标记更新、批量调度
  • React 18 默认把更新放在微任务/事件结束后的调度里（Automatic Batching）
  • 所以同一同步函数里，DOM 往往还没重渲染，读到的是旧值

正确做法：

  • React：useEffect 依赖 state、flushSync（慎用）、requestAnimationFrame / queueMicrotask 读布局
  • Vue：nextTick(() => { /* 读 DOM */ }) — 本质就是等微任务/DOM 更新后

面试答法：「状态更新异步调度，DOM 更新在后续微任务/渲染阶段，同步代码里读 DOM 会 stale。」

四、进阶 & Node

选练

Q9 · Node 和浏览器 Event Loop 有何不同？

📌 场景

同一段代码在浏览器和 Node 里输出顺序可能不同—— 写 SSR / 工具脚本时为什么要单独了解 Node 的事件循环？

查看答案

浏览器：以渲染为导向，宏任务（task）+ 微任务（microtask）+ rAF + 渲染。

Node（libuv）：分阶段循环，常见阶段：

  1. timers（setTimeout / setInterval）
  2. pending callbacks
  3. idle, prepare
  4. poll（I/O）
  5. check（setImmediate）
  6. close callbacks

每个阶段之间会清空 Node 微任务队列（process.nextTick 优先于 Promise.then）。

经典差异题：

setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));
// 在主模块顶层：顺序不确定
// 在 I/O 回调里：通常 immediate 先于 timeout

面试答法：浏览器关心渲染；Node 关心 I/O 阶段，且有 setImmediate、process.nextTick。

选练

Q10 · 定时器陷阱：嵌套 delay 与「卡死感」

📌 场景

用 setTimeout(fn, 0) 做任务切片避免长任务阻塞 UI， 但连续嵌套 5 层以上反而越来越慢——为什么？和微任务挤占有什么关系？

查看答案

浏览器规范：

  • 嵌套层级 > 5 的 timer，最小间隔 clamp 到约 4ms
  • 若微任务队列一直有新任务（死循环 Promise.then），宏任务（含 timer）永远轮不到 → 页面卡死
// ❌ 微任务饥饿：宏任务永远执行不了
function loop() {
  Promise.resolve().then(loop);
}
loop();

// ✅ 让出主线程用宏任务
function chunk() {
  doWork();
  setTimeout(chunk, 0);
}

项目建议：大量 Promise 链注意别让微任务无限排队；长计算用 setTimeout / requestIdleCallback / Web Worker 切片。
